# Orders & Products

Тестовое задание DZencode на позицию Junior+ React Developer: учёт приходов и товаров, REST API и база MySQL.

## Демонстрация

**[Открыть приложение](https://dzencode-orders-products.onrender.com)**

- Email: `demo@example.com`
- Пароль: `DemoPass123!`
- Приложение размещено на Render, MySQL — в Aiven. Render собирает ветку `main`.
- Бесплатный сервис засыпает при простое: первое открытие может занять около минуты.
- Демо-аккаунт работает с общими данными. Удаление прихода сохраняется в базе и удаляет его товары; обновление страницы не восстанавливает записи.

Видео демонстрации пока не добавлено. [Сценарий записи и итоговая проверка](docs/final-review.md).

## Возможности

- Страницы «Приходы» и «Продукты», навигация и анимация появления страниц с поддержкой reduced motion.
- Приходы: количество товаров, даты в двух форматах, суммы отдельно в USD и UAH, боковая панель связанных товаров.
- Удаление прихода с подтверждением, обработкой ошибок и обновлением обоих списков и диаграммы.
- Продукты: фильтр по типу, серийный номер, состояние, гарантия, цены и название прихода.
- Дата и часы в хедере, счётчик подключённых вкладок через Socket.io.
- Форма входа с клиентской и серверной валидацией, JWT в HttpOnly-cookie, выход с отзывом сессии в БД.
- Русский и украинский интерфейс. Язык сохраняется в localStorage, синхронизируется между вкладками и передаётся в SSR через cookie.
- SSR списков: данные присутствуют в исходном HTML, затем обновляются через RTK Query.
- Lazy Loading окна удаления и карты. Диаграмма сумм по приходам с переключением валюты.
- Карта Украины: перемещение, масштабирование, возврат к исходному виду. Без маркеров складов.

## Быстрый запуск через Docker

Нужны Git и Docker Desktop с Linux containers. Локальная установка Node.js для этого варианта не требуется. Команды ниже подходят для Git Bash, macOS и Linux.

```bash
git clone https://github.com/RomanZakrenychnyi/dzencode-orders-products.git
cd dzencode-orders-products
cp .env.example .env
```

Сгенерируйте локальный секрет:

```bash
docker run --rm node:24-bookworm-slim node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

Вставьте результат в `JWT_SECRET=` файла `.env`, сохраните файл. Остальные демонстрационные настройки подходят для первого локального запуска. Реальные `.env` не коммитятся.

Освободите порты 3000, 4000 и 3307, затем:

```bash
docker compose up --build -d --wait
docker compose ps
```

Ожидаемый статус всех трёх сервисов — `healthy`.

| Адрес | Назначение |
| --- | --- |
| http://localhost:3000 | Приложение, вход указан выше |
| http://localhost:4000/health/db | Проверка соединения API с MySQL |
| 127.0.0.1:3307 | MySQL для локального клиента |

На пустом томе автоматически создаются таблицы, 4 прихода, 3 типа, 5 товаров, 10 цен и демо-пользователь. Повторный запуск не сбрасывает данные и не меняет пароль существующего пользователя.

```bash
docker compose stop          # остановить, сохранив данные
docker compose up -d --wait   # запустить снова
docker compose logs --tail=100 api web
```

Не используйте `docker compose down -v`, если данные нужны: это удаляет том MySQL. [Подробности Docker и смена портов](docs/docker.md).

## Разработка без контейнеров для Next.js и Express

Нужны Node.js 24.x, npm 11.x и MySQL из Docker. Все команды — из корня проекта. Если приложение уже работает целиком в Docker, сначала остановите его `docker compose stop`, чтобы освободить порты.

```bash
npm ci
cp .env.example .env
cp apps/api/.env.example apps/api/.env
cp apps/web/.env.example apps/web/.env.local
```

Копируйте примеры только при первой настройке, не перезаписывайте существующие `.env`. Сгенерируйте секрет командой `node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"` и задайте `JWT_SECRET` в `apps/api/.env`. Значения `DB_PORT` и `DB_PASSWORD` API должны совпадать с корневым `.env`.

```bash
npm run db:up
npm run setup:auth
```

В первом терминале — `npm run dev:api`, во втором — `npm run dev`. Откройте http://localhost:3000. Используйте `localhost` и для интерфейса, и для API: SSR требует cookie того же hostname. [Настройка авторизации](docs/authentication.md).

## Проверки

После `npm ci`:

| Команда | Что проверяет |
| --- | --- |
| `npm test` | 16 unit-тестов расчётов, форматирования и переводов; БД не нужна |
| `npm run typecheck` | Типы интерфейса |
| `npm run typecheck:api` | Типы API |
| `npm run build` | Production-сборка Next.js |
| `npm run build:api` | Сборка Express |
| `npm run test:ssr` | Сборка и SSR с изолированным тестовым API, без реальной БД |
| `npm run test:auth` | JWT, cookie, валидация, Origin и отзыв сессии; нужны локальная БД и setup:auth |

`test:auth` читает `apps/api/.env`, создаёт и удаляет тестовую сессию, не удаляет приходы. Запускайте его на локальной тестовой БД.
Проверка общего контейнера Render описана в [docs/render.md](docs/render.md): `node --test tests/render.smoke.test.mjs` требует отдельного тестового приложения на порту 10000.

`npm run start` и `npm run start:api` запускают соответствующие production-сборки вне Docker. Каждому серверу нужен отдельный терминал.

## Архитектура и данные

```text
apps/web/        Next.js, компоненты, Redux, стили, локализация, unit/SSR-тесты
apps/api/        Express, MySQL, авторизация, Socket.io, тест авторизации
database/        schema.sql, seed.sql, миграция авторизации, модель Workbench
deploy/render/   общий Dockerfile, nginx и управление процессами
docs/            инструкции запуска, размещения и проверки
tests/           интеграционная проверка общего контейнера
```

SSR создаёт отдельный Redux store для запроса; JWT не передаётся в клиентские props. Серверные запросы используют `cache: no-store`. После загрузки RTK Query управляет запросами и инвалидирует списки после удаления. При недоступном API выводится ошибка с повтором, подстановка локальных моков не используется.

Данные интерфейса поступают из MySQL. `database/seed.sql` содержит начальный набор; `apps/web/src/data/inventory.ts` сохранён как исходный пример. Деньги хранятся целым количеством копеек/центов, без конвертации валют. Даты приходов форматируются в `Europe/Kyiv`, гарантия хранится как календарная дата.

[Схема SQL](database/schema.sql) и [модель MySQL Workbench](database/orders-products.mwb): 6 таблиц, 29 колонок, 4 внешних ключа. Открытие модели проверено в Workbench 8.0.47. Условия CHECK описаны в комментариях модели; полный исполняемый источник ограничений — `schema.sql`. [Описание БД](database/README.md).

При локальном запуске API использует `/auth/*`, `/orders`, `/products`, `/health` и `/health/db` на порту 4000. На Render эти маршруты имеют префикс `/api`; Socket.io доступен по `/socket.io/`. [Настройка размещения](docs/render.md).

## Границы задания

- Поле поиска в хедере — элемент макета, поиск не реализован. «Группы», «Пользователи» и «Настройки» неактивны; рабочие разделы — «Приходы» и «Продукты».
- Создание и редактирование приходов/товаров не реализованы. Начальные данные загружаются через SQL.
- Счётчик показывает подключения всего экземпляра приложения, а не уникальных пользователей.
- Диаграмма использует данные приходов; карта демонстрирует интеграцию и не привязана к товарам. Для тайлов OpenStreetMap нужен интернет, атрибуция сохранена.
- Переводы названий демонстрационных записей заданы словарём; неизвестные записи отображаются с исходными названиями.
- Все пользователи работают с общими данными. Регистрация, роли и восстановление пароля не входят в реализацию.
