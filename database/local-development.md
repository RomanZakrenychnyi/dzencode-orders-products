# Локальная MySQL через Docker Compose

Нужны Docker Desktop с запущенным Linux Engine и терминал в корне `test`. Compose пока запускает только MySQL; React и API запускаются отдельно. API читает эту базу, React получает приходы и товары через RTK Query.

## Первый запуск

В Git Bash скопируйте пример настроек (один раз, если `.env` ещё нет):

```bash
cp .env.example .env
npm run db:up
```

В PowerShell вместо `cp` можно использовать `Copy-Item .env.example .env`.
Корневой `.env` читает Docker Compose; это отдельный файл от `apps/api/.env`. Он исключён из Git. Пароли примера предназначены только для локальной разработки.

Команда ждёт готовности БД. При первом запуске в пустом томе MySQL выполняет `schema.sql`, затем `seed.sql`. Результат: 4 прихода, 3 типа, 5 товаров, 10 цен. Кириллица хранится в utf8mb4, даты создания — UTC. Четвёртый приход пустой.

## Проверка

```bash
npm run db:status
docker compose exec db mysql --default-character-set=utf8mb4 -uorders_app -p orders_products
```

Введите значение `DB_PASSWORD` из корневого `.env`. Пароль при вводе не отображается. Если Git Bash сообщает `the input device is not a TTY`, выполните интерактивную команду с префиксом `winpty`.

В появившейся консоли `mysql>`:

```sql
SHOW TABLES;
SELECT id, title FROM orders;
SELECT COUNT(*) FROM products;
SELECT COUNT(*) FROM product_prices;
exit;
```

Диагностика запуска: `npm run db:logs`. Не публикуйте логи, содержащие личные настройки или данные.

## Остановка и сохранение данных

```bash
npm run db:stop
npm run db:up
```

Данные находятся в томе `dzencode-orders-products_mysql_data`. Остановка и повторный запуск сохраняют записи. Обычный `docker compose down` тоже сохраняет том; добавление `-v` удаляет его и все данные БД — для обычной остановки этот флаг не нужен.

Начальные SQL-скрипты не выполняются повторно на существующем томе. Изменение `seed.sql` не обновляет существующие записи. Изменение пароля в `.env` также не меняет пароль уже созданного пользователя; это потребует отдельной команды MySQL. Изменения схемы в дальнейшем будут оформляться миграциями.

## Параметры подключения

| Параметр | Значение |
| --- | --- |
| Host из Windows | `127.0.0.1` |
| Port из Windows | `3307` (или `DB_PORT` из `.env`) |
| Database | `orders_products` |
| User | `orders_app` |
| Password | `DB_PASSWORD` из корневого `.env` |

Порт опубликован только на локальном интерфейсе Windows. Для будущего API в контейнере адресом будет `db:3306`. API, запущенный в Windows, использует `127.0.0.1:3307`. Пользователь `orders_app` имеет доступ к БД проекта, API не должен использовать `root`.

## Выполненная проверка

API читает настройки `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` из `apps/api/.env` (пример — рядом). Корневой `.env` автоматически в API не загружается. После изменения настроек перезапустите `npm run dev:api`.

Для проверки откройте:

- http://localhost:4000/health/db — `{"status":"ok","database":"connected"}`;
- http://localhost:4000/orders — массив из 4 приходов;
- http://localhost:4000/products — массив из 5 товаров с ценами.

Ответы используют формат полей React: `orderId`, `serialNumber`, `guarantee`, `price`, `amountMinor`. Даты создания возвращаются в UTC с `Z`, даты гарантии — без времени. При недоступной БД маршруты возвращают HTTP 503, детали SQL и пароль клиенту не передаются. `/health` продолжает отвечать независимо от состояния БД. React подключён к этим маршрутам через RTK Query; удаление выполняется через `DELETE /orders/:id`. При недоступном API интерфейс показывает ошибку и кнопку «Повторить».

Проверены сборка TypeScript, точное совпадение ответов `/orders` и `/products` с исходными демонстрационными данными, `/health/db`, HTTP 404 и HTTP 503 при недоступном адресе БД.

Проверены запуск до состояния healthy, число начальных записей и чтение кириллицы. Отдельная контрольная запись сохранилась после перезапуска контейнера, затем была удалена; в базе остались только демонстрационные данные.


### Удаление через API

Маршрут DELETE /orders/:id проверяет положительный целочисленный ID в диапазоне INT UNSIGNED и использует параметризованный запрос. Ответ 204 означает отсутствие прихода после операции, включая повторное удаление уже отсутствующего ID. Некорректный ID даёт 400; недоступная БД — 503. Приход, товары и цены удаляются одним атомарным каскадным DELETE.

Проверено на отдельном тестовом приходе: удаление и отсутствие записей в последующем GET, каскад товаров и цен, повторный запрос, сохранность других приходов, неверные ID и недоступная БД. Исходные демонстрационные приходы при автоматической проверке не удалялись. При ручной проверке удаление действительно меняет базу и не отменяется обновлением страницы.
