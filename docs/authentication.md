# Авторизация

## Локальный запуск

1. Запустите MySQL: `npm run db:up`.
2. В `apps/api/.env` задайте `JWT_SECRET` (случайная строка не короче 32 символов), `DEMO_EMAIL` и `DEMO_PASSWORD`. Пример остальных настроек — `apps/api/.env.example`.
3. Сгенерировать секрет можно командой:

```bash
node -e "console.log(require('node:crypto').randomBytes(32).toString('hex'))"
```

4. Выполните `npm run setup:auth`: команда добавляет `users` и `auth_sessions` в существующую БД и создаёт демо-пользователя. Приходы и товары сохраняются. Повторный запуск не меняет пароль существующего пользователя. Изменение `DEMO_PASSWORD` в файле само по себе пароль в БД не меняет.
5. Запустите `npm run dev:api` и `npm run dev` в отдельных терминалах. После изменения `.env` перезапустите API.
6. Откройте http://localhost:3000/login.

Начальные локальные демо-данные из `.env.example`: email `demo@example.com`, пароль `DemoPass123!`. Это учебный аккаунт с доступом к общим демонстрационным данным, не личная учётная запись. Для развёртывания задайте собственные настройки; реальные `.env` исключены из Git.

## Поведение

- React Hook Form и Zod проверяют формат email и длину пароля 8–128 символов. Сервер независимо выполняет ту же валидацию.
- `/auth/login` проверяет scrypt-хеш с индивидуальной случайной солью. Ответ для неизвестного пользователя и неверного пароля одинаковый. Пароль и его хеш не возвращаются клиенту.
- JWT подписывается HS256, содержит идентификаторы пользователя и сессии, issuer, audience и срок 8 часов. Проверка ограничена этим алгоритмом и этими issuer/audience. Токен хранится в HttpOnly-cookie `orders_session`, а не localStorage или Redux. Cookie имеет SameSite=Lax и Secure в production.
- Сессии хранятся в MySQL. `/auth/logout` отзывает текущую сессию и очищает cookie: скопированный JWT этой сессии после выхода тоже недействителен. Другие браузерные сессии остаются активны. Просроченные записи очищаются при успешном входе.
- `/auth/me`, GET `/orders`, GET `/products` и DELETE `/orders/:id` требуют действующую сессию. Без неё возвращается 401. Публичный `/health` проверяет работоспособность процесса; Socket.io передаёт только число подключений.
- Изменяющие запросы требуют точного Origin из `CLIENT_ORIGIN`, включая запросы через curl/Postman. CORS разрешает этому интерфейсу отправлять cookie. На развёртывании интерфейс и API должны использовать HTTPS и один site (например, поддомены одного домена); разные независимые домены с этой cookie-конфигурацией не поддерживаются.
- Лимит входа — 20 попыток за 15 минут с одного IP в одном процессе API; при превышении возвращается 429. Распределённый rate limit, восстановление пароля, регистрация и роли пока не реализованы.
- Интерфейс скрывает рабочие страницы до проверки входа. При 401 переводит на `/login` полной навигацией, очищая клиентский кэш. Проверка сессии повторяется раз в минуту и при запросах. После выхода кнопка Back не даёт доступа к защищённому API.
- Все авторизованные пользователи имеют доступ к общему набору приходов; многопользовательское разделение данных не реализовано.

## Проверка

```bash
npm run test:auth
```

Интеграционный тест требует работающей локальной MySQL и созданного демо-пользователя. Проверяет валидацию, неверный пароль, запрет доступа без сессии, cookie, вход, поддельный и просроченный JWT, Origin и отзыв JWT после выхода. Созданная тестовая сессия удаляется, приходы не изменяются.

Ручная проверка: пустая форма → ошибки полей; неправильный пароль → сообщение; правильные данные → приходы; перезагрузка сохраняет вход; «Выйти» → форма входа. При остановленном API показывается ошибка с возможностью повторить попытку.

`database/schema.sql` содержит полную структуру из шести таблиц для новой БД. Для существующей базы используется повторяемый скрипт `database/migrations/002_auth.sql` через `setup:auth`; это пока не полноценный версионированный инструмент миграций.
